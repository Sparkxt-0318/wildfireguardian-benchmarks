Nothing, by decision. See WG-D-018: the suite stops growing here. A benchmark is
added only when a real project failure exposes a missing case — not because a

## Open questions for the programme

1. **Which conventions are WildfireGuardian's?** This suite declares interval
   safety (WG-SEM-1), opt-in waiting (WG-SEM-2) and loss-derived decision
   thresholds (WG-PRB-2). If a production component has chosen differently, the
   right response is a variant benchmark, not a weakened one — but somebody has
   to say which convention is the programme's.
2. **Where do the loss matrices come from?** Half the K and L results turn on a
   threshold derived from losses invented for the benchmark. `WG-BM-047`'s
   threshold of 0.01 follows from a 99:1 ratio between an entrapment and a
   delay; whether that ratio is the programme's is not a question this
   repository can answer, and `WG-BM-062` shows a recommendation turning on 0.21
   of expected loss.
3. **What is the acceptable-loss threshold?** The J and L families use 10 and 8
   in scenario-local units. A real threshold is a policy decision and would let
   the protectability benchmarks carry operational meaning.
4. **Is sup-regret used anywhere operationally?** `WG-BM-036` shows it moving
   mechanically with ensemble size. If something consumes it, that consumer needs
   the ensemble provenance alongside the number (gap G-12).

## Housekeeping

- Reports under `reports/` are generated except `KNOWN_GAPS.md`,
  `BENCHMARK_READINESS.md`, `BENCHMARK_SELF_AUDIT.md`,
  `INTEGRATION_COVERAGE.md` and `V0_1_SCIENTIFIC_AUDIT.md`. Regenerate the rest
  with `python -m wg_benchmarks report`.
- `benchmarks/` is generated by `tools/authoring/*.py`; edit the scripts.
- Generation is deterministic — no timestamps, no timings — so a regenerated
  report is a no-op diff unless something changed.
